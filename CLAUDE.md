# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Stack

Static SPA, no build step: vanilla JS with ES modules, HTML, CSS. No `package.json`, no bundler/transpiler, no test framework, no linter/formatter. UI text is in Thai (`lang="th"`).

- **Backend**: Supabase (Postgres + Auth). Client initialized once in `js/supabase-config.js`.
- **CDN libs** (loaded directly in `index.html`, no npm): `@supabase/supabase-js@2`, SheetJS `xlsx@0.18.5` (Excel import), `exceljs@4.4.0` (styled Excel export), Google Fonts (Sarabun).
- **Edge function**: `supabase/functions/admin-create-user/index.ts` (TypeScript, runs on Supabase, not part of the frontend bundle).
- **Deploy**: Vercel, auto-deploys on push to `main`. `vercel.json` is just an SPA rewrite (`/(.*) -> /index.html`) — no build command.

## Gotchas

- **Supabase key is intentionally hardcoded** in `js/supabase-config.js` (URL + anon/publishable key). This is a publishable key protected by RLS — do not "fix" this by moving it to env vars or a `.env` file; that would break the static Vercel deploy, which has no build step to inject env vars.

- **Report date attribution — ONE rule, used by every report.** This is the #1 recurring bug source (8+ commits fixing regressions). Read this before touching any month/date logic.

  `end_date` (employees) and `date` (movements) hold the **termination date** — the first day the person is *no longer* working. The month a separation belongs to is the month of the **last working day**, i.e. termination date minus one day.

  **All of this lives in one place now — `js/app.js`. Do not re-define it per report; that duplication is what caused the repeat regressions.**

  - `sepYM(dateStr)` — subtracts 1 day, returns `"YYYY-MM"`. The separation month.
  - `isActiveAtMonthEnd(e, ym)` / `hcAtMonthEnd(emps, ym)` — excludes when `sepYM(end_date) <= ym`, and excludes not-yet-hired when `join_date > lastDayOfMonth(ym)`. It deliberately uses **the same `sepYM`**, so a person leaves the headcount in exactly the month their separation is counted and the balance below can never drift.
  - Separations: `sepYM(e.end_date) === ym` (employees) / `sepYM(m.date) === ym` (movements). **Not `movYM`** — `movYM` does not subtract the day.
  - New hires: `join_date` month, and `movYM` for New Hire movements.
  - **Canonical case:** termination 1 Aug 2026 → last working day 31 Jul → separation counted in **July**, person **excluded from July's** headcount, still counted in June.
  - Balances exactly: Opening + New Hires − Separations = Ending.

  Confirmed with the user on 2026-08-03. This flipped twice that day: a written spec asked for the separation to sit in August (the termination date's own month), but on seeing real numbers the user confirmed **July**. If a future request says "August", check it against this line before changing anything.

  Regression tests (no browser or Supabase needed):
  ```
  osascript -l JavaScript test/headcount-date.test.js   # 46 cases
  osascript -l JavaScript test/dashboard.test.js        # 33 cases
  ```
  They extract the real functions from `js/app.js` and assert the other reports do not re-define their own copies.

- **Shift allowance rules, all confirmed against the hand-worked July 2026 answers on 2026-08-18.** Do not change any of these without checking with the user first — they were settled by reconciling against real payroll figures, not from a spec.
  - **Work out what the month would pay with no absences, then deduct the absent days.** This is two separate steps and they must stay separate.
    1. **The base.** A fully-worked month always pays the full monthly rate, whatever the month's length — February with 28 payable days pays 1,800, the same as July with 31, because a short month must not shortchange anyone. An incomplete *employment window* is pro-rated at monthly rate ÷ 30 flat (*not* ÷ days-in-month). "Complete" is measured against the calendar month, not the employment window, so someone hired mid-month who worked every day they were employed is still pro-rated — the July answer key pays that case 60 × 19 = 1,140, not the full rate.
    2. **The deduction.** Each day that does not pay costs monthly rate ÷ 30, always, in every month. July absent one day pays 1,800 − 60 = 1,740; February absent one day pays the same 1,740.
    `DAILY_DIVISOR`, `absentDays`, `baseWholeMonth` in `js/shift-allowance.js`.
    **⚠️ Only genuine non-paying days are deducted** — absence, unpaid leave, suspension, `CHECK_NOTE`, and unapproved long sick leave. Days dropped by a *shift rule* are not absences and must never be deducted: the NOR days in a NOR+N03 month, and a Process employee's N03 days. Deducting those would charge the person twice for the same day.
    **History:** the user settled the ÷30 divisor on 2026-08-18. It was applied as `payDays × rate ÷ 30` capped at the monthly rate, which made **the first absent day free in any 31-day month** (30 × 60 already hits the 1,800 cap). The user spotted that on 2026-09-21 and chose to deduct every absent day. That supersedes the old worked example of "February missing one day pays 1,620" — it now pays 1,740. No verified answer-key case was contradicted: the July key's 30-day case (AKR23030950 → 1,800) is a 30-day *employment window* with no absence, not a 31-day month with one absence, and it still pays 1,800.
  - **Days outside employment are dropped before counting.** Timesheets run to month end even for people who left mid-month. A day counts only when `join_date <= date` and `date < end_date` — `end_date` is the first day *not* worked, the same rule the reports use. Accuracy depends entirely on `join_date`/`end_date` being correct, so the page lists everyone affected.
  - **NOR alternated with N03 pays only the N03 days.** `NOR` is ordinary working hours, not a shift. When the payable shift codes are exactly `{NOR, N03}`, the rate is still the two-family 1,200 but only N03 days earn it. Confined to that exact pair — `NOR`+`N01`, `NOR`+`A01`, or a third code alongside all keep whole-month averaging. `PAY_ON_SHIFT_ONLY` in `js/shift-allowance.js`. **F08 with any day-family code** (NOR / D01 / D02 / D03 / F03 / F04, `withFamily: "DAY"`) follows the same rule — F08 = new night shift; user 2026-10-16: people on F08 for a few days next to D01 or NOR were getting the full two-family 1,200 — including the >15-day full-month threshold. N03 stays limited to the exact NOR pair.
  - **Process staff earn nothing for N03 days**, other shift days pay normally, and the family count is left alone. Membership is guessed by looking for "process" in the employee's division/department/section/team/position (`isProcessEmp`), so the page lists everyone it caught.
  - **A month spent only on NOR and F01 pays nothing.** Checked against the shift codes directly, not the families, so it holds however F01 is classified later (it is unmapped today). `NO_PAY_CODE_SETS`.
  - **Above 15 N03 days the NOR+N03 month pays a flat 1,200** instead of per-day. The 15 counts N03 days plus payable rest/leave days inside the rotation; exactly 15 stays per-day. `N03_FULL_THRESHOLD`.
  - **A month with no `WORKED` day pays nothing until HR approves that person**, which is how long sick leave still gets paid. Approvals are per employee-month, held in memory only, and cleared on a new upload.
  - **Suspension pays nothing for that day; unpaid leave and absence already did.** Suspension and sick leave are read from a column detected by name, falling back to keyword-matching the free-text note column, which is where they actually live (`detectExtraCols`, `isSuspendRow`, `isSickRow`). The page names the columns and lists every note phrase it acted on, because prose matching is easy to get wrong.
  - **A note saying the day was unpaid wins over the leave columns.** `ไม่จ่ายเงิน`/`ไม่รับค่าจ้าง`/`หักเงิน`/`unpaid` in the note makes the day unpaid even when `Leave_No_Deduct` is set — real July notes read "ลาป่วยไม่จ่ายเงินหักเงิน" and were being paid. `isUnpaidNote`.
  - **Sick leave running 3+ consecutive days is not paid** (`SICK_RUN_WARN`). Weekly rests and holidays *bridge* a run without counting toward its length — otherwise sick-sick-rest-sick-sick reads as 2+2 and escapes — while an ordinary working day breaks it. The bridged rest day itself still pays. HR approval restores the withheld days.
  - **`solo_rate` on `master_shift_codes`** overrides the single-family zero: N03 pays 1,200 worked alone all month. It applies only when that code is the *only* one worked; mixed with others, the ordinary family count applies. Add exceptions in the DB, never in the source.

- **Shift allowance: one shift family all month pays nothing — this is intended, not a bug.** The rate comes from how many shift *families* (เช้า/บ่าย/ดึก) a person actually worked that month — **only `WORKED` days count** (user 2026-10-16: codes left on holidays/leave days, e.g. N01 scheduled on rest days of a D01-only person, were turning 1 family into 2 → 1,200; months with no worked day still use the payable days so HR can approve long sick leave). Same for the code sets (NOR+N03 / NOR+F08 / NOR+F01): 3 families → 1,800/month, 2 → 1,200, **1 or 0 → 0**. So an O-level employee who worked only the morning shift every day of the month earns ฿0 in shift allowance, even with a full 31 payable days. Confirmed with the user on 2026-08-18 after they saw a real case (AKR17030409, O3, เช้า only, ฿0). The allowance pays for *rotating* between shifts, not for working shifts as such. Do not "fix" this by paying a floor amount for a single family.

- **Diligence allowance (เบี้ยขยัน)** — `js/diligence-calc.js` (pure, tested by `test/diligence.test.js`) + `js/diligence.js` (page) + `sql/schema_diligence.sql`. Rules from the company regulation effective 1 Sep 2026, plus details the user confirmed on 2026-10-09:
  - Time data of month M pays with month M+1's salary. Input is three raw TigerSoft exports (processed report, เพิ่มเวลา, เพิ่มเวลา-web), read by header labels, not fixed columns.
  - In scope: Permanent, job level O/S, Thai nationality only (foreigners excluded, confirmed 2026-10-09; blank nationality is included but flagged), employed the whole month, past probation (probation ends with effect on day 119, the join date being day 1 — user 2026-10-12; counting from the 1st of the next month).
  - Lose the month for: absence, **any** late/early minute, any leave except ลาพักร้อน and ลาหยุดชดเชย, more than 2 counted time-edit days, off-site time entered after the 7th of the next month, HR denial (suspension 4.9 / accident 4.11).
  - Time edits are counted **per day**, and only when the person entered the **check-in** leg by hand (confirmed 2026-10-09): check-in scanned + check-out entered by hand is let off, because the risk is someone arriving late, not scanning, and entering an on-time check-in later. The leg is found by matching the entered punch to the processed report's in/out time (night-shift check-outs land on the shift's date); a punch that is neither the in nor the out time is not counted. By reason group: ลืมบัตร/บัตรหาย/blank = counted (even "ลืมบัตรแต่เซ็นที่ป้อมยาม"); รปภ./ป้อม/ไฟดับ = company, not counted; "สแกนไม่ติด" without saying where = not counted but flagged for HR; WFH/off-site/BKK = not counted but has the 7th deadline; HR-added = not counted. HR can regroup any day on screen.
  - Forgot-card (ลืมบัตร/บัตรหาย) is the exception to the check-out leniency (confirmed 2026-10-09): forgetting it all day (both legs entered) = 1 counted time; forgetting it for one leg only — either leg — also counts 1 and is flagged "suspicious" for HR to decide, because the other leg was scanned, so the card was there.
  - Holidays (day type H/HD) are ignored entirely — people come in for OT — so lateness, leave, or time edits on a holiday never cost the allowance (confirmed 2026-10-09).
  - HR edits (like the shift-allowance page): per row grant / deny / fixed amount, reason required, on the calculate screen and on saved months (history → `diligence_edit`). The system's own result is kept in `auto_qualified` / `auto_amount` so an edit can be cleared. A fixed amount of 0 means "don't pay this month" but the month still counts toward the streak. HR edits survive re-uploading the same month's files: per-person edits come back from `diligence_results.manual` and regrouped time-edit days from `diligence_runs.edit_groups`. Once a later month is saved, an earlier month's qualified/streak is frozen (amount-only edits) because the later streak was counted from it.
  - Rate by consecutive qualifying months: 1–3 → 300, 4–6 → 600, 7+ → 1,000; a miss restarts at 1 the next month. Sep 2026 is month 1 for everyone. Streaks come from the **saved** previous month, so months must be saved in order (`diligence_save` refuses to overwrite a month when a later one exists).
- **OT audit (ตรวจโอที)** — `js/otaudit-calc.js` (pure, tested by `test/otaudit.test.js`; reuses `parseProcessed` from `diligence-calc.js`, which also reads the per-rate OT columns) + `js/otaudit.js`. Compares TigerSoft's "รายงานการขอโอทีปกติ" with the processed report and lists what HR must fix in TigerSoft. Audit results are not saved; `sql/schema_ot_audit.sql` holds only shift times (`ot_shift_times`, kept apart from `master_shift_codes` so the shift-allowance families are untouched) and the team-shared "fixed in TigerSoft" ticks/notes (`ot_audit_marks`). Menu borrows `page.shiftallow` via `PERM_ALIAS`. Rules confirmed 2026-10-12:
  - **Amounts are compared against what was requested, not against shift times** (user, 2026-10-12: "most hours match what they asked for — why make me check them"; the old shift-time model flagged 231 person-days in Sep 2026, mostly correct ones, and showed 4:30 asked where the request said 3:30). Per person-day: each request's "รวม" (TigerSoft already deducted the break — never deduct again), exact duplicates dropped, truly overlapping windows counted once (a B lunch request inside an S/E window is not an overlap), clipped by the scans, floored to 30 min per request. Holiday with a request whose "รวม" equals its full window (break not deducted yet): F01 −60 min (≥9 h), NOR −60 min (window covers 12:00–13:00; the NOR break is 1 h, user 2026-10-12) minus any lunch-OT request inside 12:00–13:00. Sep 2026: 105 person-days left to check, all money-relevant.
  - Shift times (`ot_shift_times`, guessed by `inferShiftTimes`, confirmed by HR; hours-counted shifts via `by_hours`/`hours_span`) no longer change amounts; they feed the 3× rate check (confirmed shifts only) and the position note. `expectedOT`/`expectedByHours` remain exported but the audit doesn't use them for the comparison.
  - Must-check (`warn`): amount differences, level/I-O mismatch, F01 lunch-block, F01 holiday OT1 9:30, wrong day, 36 h/week, rate, duplicates TigerSoft actually paid twice. Notes (`info`): TigerSoft above what the scans support but within the request (`overscan` — typically F01 counted from clock-in), scan not covering the request (TigerSoft cuts by scan itself), before/after-shift position, OT on a leave day, wrong type on a holiday, lunch OT, overlaps, more than requested.
  - TigerSoft paying **more than requested** means HR already corrected it by hand (user, 2026-10-12) — shown as a note ("แก้มือแล้ว"), not an error. On **F01**, a lunch-OT request makes TigerSoft drop the other OT types, so those days need a manual fix; when TigerSoft is short on such a day it is flagged specifically (`LUNCH_BLOCKS_OTHERS`).
  - Weekly cap: TigerSoft OT per person per Monday–Sunday week above 36 h is flagged (labour law), excluding rate 1×/2× (holiday work within normal hours isn't legal OT). OT rate by the calendar day the OT actually falls on (confirmed 2026-10-12): a workday shift whose OT runs past midnight into a holiday / public holiday (e.g. 23:30–08:00 then 08:00–12:00) must be 3×; 3× with no part on a holiday is wrong (`holidayPart`). Sep 2026's 14 night-shift 3× cases are all correct under this rule.
  - Types S = before shift, B = lunch, E = after shift; I = paid (O level), O = time off (S/M level) — a level/I-O mismatch is flagged. Holidays must be requested as S. Lunch OT can't be checked against scans, so it is only a warning. F01 on a holiday must show OT1 8:30 (9:30 minus the 1-hour break).
  - A request is matched to the requested date's shift first, then to the after-midnight part of that shift, then to the previous day's shift — never further, so mis-dated requests surface (paired with a nearby day that has TigerSoft OT but no request). TigerSoft ties a request to the shift of the date written on it, so the previous day's shift is tried only when the requested date's shift has no scan overlap at all; a request matched to the *previous* day's shift (e.g. N01 of the 26th, "after shift" 08:00–09:00 dated the 27th) is not paid by TigerSoft; the user (2026-10-12) treats that as correct — it is left out of the expected amount and shown as a note (`nextday`). Scan coverage tolerates 5 minutes.
  - All times are minutes counted from the Excel serial, never `Date` — the older offline OT_Audit workbook showed scan times 7 hours early because it went through UTC.
